Part 1: The Evaluation Framework


The Primer: Your evaluation one-liner
First, summarize what you will measure, on which agent and cases, and against which pass bar.
I will measure [METRIC SET] on [AGENT FROM WEEK 3] using a golden dataset of [N] cases covering [SCENARIO TYPES], with [JUDGE METHOD]. Pass bar: [TARGET %s + LATENCY + COST]. I will compare [BASELINE] vs [POST-IMPROVEMENT] using [SPREADSHEET OR LANGSMITH].


Worked example
I will evaluate my Multi-Agent Deal Review Pipeline on red-flag recall, summary faithfulness, end-to-end task completion, and p95 latency using 40 historical deals (15 closed-won, 15 closed-lost, 10 edge cases) covering missing-MEDDPICC, exception-flagged, and large-deal scenarios. Judges: LLM-as-judge for faithfulness; exact-match for red flags. Pass bar: 85% recall, 90% faithfulness, 100% completion, p95 <2 minutes, $2/run. I will report baseline-to-improved deltas from LangSmith traces.

Three rules for evaluation design
Tie metrics to user outcomes: did the manager catch a red flag they would have caught manually? A generic “helpfulness score” is insufficient unless it predicts user value.
Use a golden dataset with known correct outputs, preferably from real usage. You or a domain expert must label each case.
Prove improvement with before/after evaluations and measured deltas; a prompt change that feels better is not evidence.

Part 3: Building Your Golden Dataset


Build a representative golden dataset of 30–50 cases; unrepresentative cases produce misleading scores.
Scenario mix
Use this approximate mix across your 30–50 cases.
Scenario type
Share
What it includes
Happy path
50%
Common, well-formed inputs the agent must handle reliably.
Edge cases
30%
Ambiguous inputs, partial data, multiple valid answers, and out-of-scope questions requiring graceful refusal.
Known failures
15%
Known difficult or failing cases, including those omitted from demos; measure improvement here.
Adversarial
5%
Prompt injection, jailbreaks, irrelevant questions, and malformed inputs to test guardrails and refusals.


Where to source cases
Sources below are ranked; prefer real data.
Real user data (preferred)
Production logs, ticket archives, past Slack threads, historical emails, real PRs from your repo. Anonymize first.
Synthetic from real seeds
Use an LLM to paraphrase real cases, swap entities, or vary difficulty; label manually.
LLM-generated
Last resort; useful for adversarial cases. Keep below 20% of the dataset and verify generated labels.
Public benchmarks
MS MARCO, HotpotQA, AgentBench, etc.: useful sanity checks, rarely task-specific. Do not rely on them alone.


Golden dataset rules
Every case needs a known correct answer or expected behavior. Label it before scoring, or exclude it.
For the LangSmith route, store cases as a LangSmith dataset via its UI or SDK, rather than only a CSV, to rerun evaluations and compare versions.
Tag the dataset version and use it for both baseline and re-evaluation; changing cases invalidates the delta.

Part 4: LangSmith Playbook


Use LangSmith to record structured traces, evaluate, and compare agent runs.
Create one trace/case with child runs for agent steps, LLM calls, and tools. Reuse the trace structure and metadata schema across baseline and improved runs.
Minimum viable setup
1. Create a project
Create an agent-named LangSmith project (e.g., “deal-review-eval”) to organize traces and evaluation runs; use the golden dataset for both runs.
2. Configure LangSmith
Install langsmith and relevant LangChain/LangGraph integrations. Set LANGSMITH_TRACING=true, LANGSMITH_API_KEY, LANGSMITH_PROJECT, and LANGSMITH_ENDPOINT. Never commit keys or include secrets/customer PII in trace inputs, outputs, or metadata.
3. Verify one trace
Run one case end to end. Verify its trace and LangGraph/model child runs, with case ID, run name, prompt version, expected/predicted output (true/predicted category for tickets), correctness, and timing/error metadata. Fix tracing before continuing.
4. Upload your golden dataset
Upload via LangSmith’s Datasets UI or `client.create_dataset()`. Include inputs, expected outputs where applicable, and scenario type/difficulty metadata.
5. Write your evaluators
Register evaluators with the dataset: score-returning Python functions for code-based checks, or a prompt template plus model for LLM-as-judge.
6. Run the eval
Run client.evaluate(agent, data, evaluators) or the provided notebook’s evaluation loop. Each case needs a result row and trace with matching case ID, run name, prompt version, expected/predicted output, and correctness. Keep the baseline trace structure and metadata schema for improved runs.
7. Compare runs
In LangSmith’s Comparison view, inspect metric deltas, per-case improvements/regressions, and trace differences. Link each score or spreadsheet row to its trace using the case/example ID.


What to monitor in production
Define production alerts beyond batch evaluation. Keep stable agent/prompt version, run name, environment, and case ID metadata so anomalies link to specific runs.
Quality drift
Faithfulness or task-completion drops by more than X% over a 7-day rolling window.
Cost spike
p95 cost-per-run exceeds budget by more than 25% over 24 hours (often signals a retrieval or tool-loop regression).
Latency regression
p95 latency exceeds SLA on more than 5% of runs.
Guardrail trips
Any refusal, PII redaction, or escalation rate change of more than 2x baseline.
Tool failure rate
Any single tool exceeds 5% failure rate over 1 hour (often signals an external dependency outage).

Part 5: Improvement Playbook


Choose 3–4 changes targeting your dominant baseline failure. The levers below are roughly ranked by impact per hour.
Lever
What to try
Symptoms it fixes
Prompt engineering
Refine the system prompt, add few-shot examples, restructure the task, or specify refusals.
Hand-waving in instructions, inconsistent format, refusal failures, tone drift.
Retrieval tuning (RAG)
Re-chunk, switch embedding model, add re-ranking, switch to hybrid search, expand query, filter by metadata.
Faithfulness failures, irrelevant context, missing answers when info exists in corpus.
Tool design
Rewrite tool descriptions, split multi-purpose tools, validate inputs, or return richer errors.
Wrong tools, repeated tool calls, malformed inputs.
Control flow
Change patterns (ReAct → plan-execute; single-agent → supervisor), cap steps, or add planning/verification.
Excessive tool calls, missed steps, giving up, poor recovery from partial failures.
Model upgrade
Use a larger/newer model for the critical step; often costly, sometimes the only fix.
Reasoning failures on complex multi-hop or multi-step tasks that prompt engineering cannot fix.
Add guardrails
Pre-call input filters, post-call output filters, structured output schemas, explicit refusal triggers.
Hallucinations, PII leaks, unsafe content, format violations.
Human-in-the-loop
Require approval before writes or review low-confidence outputs.
High-stakes failures where human review reduces the risk of harm.


How to report improvements
For each of 3–4 improvements, report the lever, change, targeted failure cluster, predicted impact, and measured delta. Example: “MiniLM → BGE-large for long-context faithfulness failures; predicted +5% faithfulness; measured +7%, with p95 latency +400ms.”
Report regressions and negative deltas; they are useful evidence.
